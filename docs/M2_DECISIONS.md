# M2 — Architecture Decision Records to Adapt

These decisions express a proposed architecture. Codex should capture implementation-specific decisions, alternatives and actual trade-offs in the repo's `docs/decisions/` style. Do not represent unimplemented assumptions as facts.

## ADR-M2-001: Immutable stock movements and derived estimated balance

**Context:** Simple product quantity mutation offers poor auditability and obscures reasons for changes. Offline stores can diverge from the cloud.

**Decision:** Keep append-only movements and a fast local projection composed of last known confirmed baseline + pending local delta. Update the movement and projection in the same SQLite transaction, with the command outbox.

**Alternatives:** (a) `products.quantity` only, (b) sum movement log for every screen, (c) confirmed snapshot plus pending ledger and cached projection.

**Why:** Append-only history is auditable; a cached projection keeps list screens responsive and can be reconciled after M4 sync. Must test projector consistency. `base_quantity + pending_delta` is an estimate, not server guarantee.

**Trade-offs:** Extra tables and discipline required so the pending delta matches the movement history. M4 needs a precise acknowledgement/rebase algorithm to prevent double counting.

## ADR-M2-002: One command per sale, not one command per stock movement

**Context:** Saving a sale creates several stock movements.

**Decision:** A sale creates one `sale.create` command with sale and all item snapshots. Negative movements generated by that sale reference this command, but do not enqueue their own `inventory.adjust` commands.

**Why:** Atomic business intent prevents applying stock deduction twice on the future server.

**Trade-offs:** The server command executor must create all affected stock movements and validate all lines in one transaction.

## ADR-M2-003: Immutable sale price snapshots and safe integers

**Context:** Product prices change after selling. JavaScript floats can introduce small money errors.

**Decision:** Historical sale items store immutable SKU/name/price snapshots, quantity and integer-kobo line total. At checkout, re-read product values and recompute totals inside transaction; if price changed since review, block and request reconfirmation.

**Alternatives:** Derive history from current products (rejected), use floating-point NGN amounts (rejected), introduce a decimal math library (not needed for integer quantity and 2-decimal NGN MVP).

**Trade-offs:** Additional snapshot columns and validation of integer bounds.

## ADR-M2-004: Local provisional stock and negative-stock prevention

**Context:** Two disconnected devices may both believe stock is available. M2 has no server sync.

**Decision:** Locally block a sale/adjustment that exceeds estimated availability, under serialized transactional writes. Mark all local sales and movements as pending, with no claim of authoritative confirmation.

**Trade-offs:** Local correctness cannot guarantee remote availability. M3 server locks/stock checks and M4 conflict handling remain essential.

## ADR-M2-005: Stable checkout attempt idempotency

**Context:** Rapid double taps or app termination after a successful local commit can cause duplicate sales on retry.

**Decision:** A single logical checkout has a stable `checkout_request_id`; a unique constraint plus transactional pre-check returns the original sale for repeated submission. New checkout starts a new ID.

**Trade-offs:** UI must preserve/reuse request IDs appropriately during retries, and change to a new ID only when intentionally starting a new sale. Future server command ID is a separate idempotency boundary.

## ADR-M2-006: Data-preserving outbox schema migration

**Context:** M1 outbox may contain a SQL CHECK constraint that accepts only product command types.

**Decision:** Inspect actual schema; if necessary, perform a safe versioned schema migration that broadens allowed types, preserves existing M1 command IDs/payloads/order and validates FKs and rollback. Never reset the database.

**Trade-offs:** SQLite table rebuilds have careful FK/transaction sequencing. Automated migration from a populated M1 database and on-device verification are mandatory.
